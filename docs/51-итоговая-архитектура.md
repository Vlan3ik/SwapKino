# Goal 51: итоговая архитектура рекомендаций

## Границы данных

TMDB является единственным каталогом. В PostgreSQL не создаётся сущность фильма: контент адресуется парой `media_type + tmdb_id`. В продуктовой базе остаются только:

- пользовательское состояние (`rating`, `watched`, `favorite` и подавление);
- impressions;
- `UserTasteFeature` с весом, confidence и числом наблюдений;
- конфигурация киноплёнки (`Filmstrip`, feature rules и references);
- маленький `KeywordAlias` справочник для русской админки.

Совместимые типы `Movie*`, `CatalogSyncState` и hardcoded `ThemeRegistry` оставлены только для старых тестовых контрактов; они исключены из EF-модели. Миграция `RemoveTmdbCatalog` удаляет соответствующие таблицы, поэтому новый runtime не может записать фильм в PostgreSQL.

## Runtime flow

`GET /api/v1/filmstrips/{slug}/feed` загружает конфигурацию киноплёнки и taste profile, вызывает четыре независимых TMDB source: personalized discover, plain discover, one-hop recommendations и one-hop similar. После объединения применяются deduplication, rated/watched/recent exposure guards, локальный `RecommendationRanker` и `DiversityReranker`. Итоговый deck сохраняется в Redis с ключами пользователя, версии профиля, slug и `config_version`.

Frontend получает только первую часть deck и карточки через `TmdbCardGateway`. Карточки кэшируются в Redis; TMDB payload не записывается в PostgreSQL.

## Операционные границы

1. Import matching использует TMDB search и сохраняет только внешний идентификатор в import workflow.
2. Preview показывает strict/relaxed анализ и результаты по каждому reference.
3. Исторические migration-файлы сохраняются для воспроизводимости, но актуальная схема после `RemoveTmdbCatalog` не содержит movie/catalog tables.
